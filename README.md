# Self-Hosted GitHub Actions Runner on AWS EC2

Configure and run a self-hosted GitHub Actions runner on an Ubuntu EC2 instance. This project demonstrates how to connect GitHub Actions to your own cloud virtual machine, execute Linux commands through a workflow, and configure the runner as a persistent Linux system service.

## Project Overview

GitHub Actions automates software development workflows such as testing, building, and deployment. By default, workflows commonly run on GitHub-hosted runners. With a self-hosted runner, you can use a machine that you manage.

In this project, I configured an AWS EC2 Ubuntu instance as a self-hosted GitHub Actions runner. I registered the runner with my GitHub repository, executed a workflow to inspect the EC2 environment, verified the successful job execution, and installed the runner as a `systemd` service.

### Project Highlights

- Launched an Ubuntu EC2 instance on AWS.
- Connected to the instance securely using SSH and a PEM key.
- Configured a GitHub Actions self-hosted runner.
- Executed a workflow on the EC2 instance.
- Verified the Linux environment using shell commands.
- Installed and started the runner as a Linux system service.
- Checked the runner service status and GitHub Actions execution logs.

## Prerequisites

- A GitHub account and repository.

- An Ubuntu EC2 instance with network connectivity.
- An SSH key pair for connecting to the instance.
- Basic knowledge of Git, Linux, and GitHub Actions.

## Step 1: Launch an EC2 Instance

1. Open the AWS Management Console.
2. Navigate to EC2 and choose **Launch instance**.
3. Select Ubuntu Server as the operating system.
4. Choose an instance type suitable for the workload and budget.
5. Select a VPC and subnet with the required network connectivity.
6. Configure a security group to allow SSH (TCP port 22) only from your trusted public IP address.
7. Select or create a key pair and securely store the private key.
8. Launch the instance.

**Security note:** Avoid exposing SSH to the entire internet. Review EC2, storage, and public IPv4 charges before launching resources.

## Step 2: Connect to EC2 Using SSH

From my WSL terminal, I copied the PEM key into the Linux home directory and restricted its permissions.

```bash
mkdir -p ~/.ssh
cp /mnt/c/Users/js171/Downloads/self_runner_lab.pem ~/.ssh/self_runner_lab.pem
chmod 400 ~/.ssh/self_runner_lab.pem
```

Connect to the instance using its current public IPv4 address:

```bash
ssh -i ~/.ssh/self_runner_lab.pem ubuntu@YOUR_EC2_PUBLIC_IP
```

Replace `YOUR_EC2_PUBLIC_IP` with the instance's current public IP address.

Verify the connection:

```bash
whoami
hostname
uname -a
df -h
```

Expected observations:

- The login user is `ubuntu`.
- The hostname identifies the EC2 instance.
- `uname -a` displays Linux system information.
- `df -h` displays filesystem capacity and available disk space.

## Step 3: Download and Configure the Runner

On the GitHub repository, navigate to:

**Settings → Actions → Runners → New self-hosted runner**

Select Linux and the appropriate architecture. Copy the current download and configuration commands provided by GitHub.

In the EC2 terminal, create a directory and download the runner package using the URL shown on the GitHub setup page.

```bash
mkdir actions-runner
cd actions-runner
```

Download and extract the package using the commands generated by GitHub. Verify the package checksum against the expected checksum displayed on the official setup page before extracting it.

Then run the configuration command supplied by GitHub:

```bash
./config.sh --url https://github.com/YOUR-USERNAME/YOUR-REPOSITORY --token YOUR_NEW_TOKEN
```

Replace the placeholders with your repository URL and a fresh runner registration token. Do not publish or share the token.

During configuration:

- Use the default runner group unless another group is required.
- Accept the default runner name or choose a descriptive name.
- Keep the default labels for this lab.
- Accept `_work` as the work folder.

Successful configuration should confirm that the runner was added and its settings were saved.

## Step 4: Start the Runner and Verify Connectivity

Start the runner interactively for the first test:

```bash
./run.sh
```

The terminal should display a successful GitHub connection and a message indicating that the runner is listening for jobs.

In GitHub, open **Settings → Actions → Runners** and verify that the runner is online.

The default labels used by this lab are:

- `self-hosted`
- `Linux`
- `X64`

## Step 5: Create the GitHub Actions Workflow

Create this file in the repository:

`.github/workflows/self-hosted-runner.yml`

```yaml
name: EC2 Self-Hosted Runner Lab

on:
  workflow_dispatch:

jobs:
  inspect-ec2:
    runs-on: [self-hosted, linux, x64]

    steps:
      - name: Show runner hostname
        run: hostname

      - name: Show operating system
        run: uname -a

      - name: Check disk space
        run: df -h

      - name: Confirm self-hosted runner
        run: echo "My GitHub Actions job ran on AWS EC2!"
```

### Workflow Explanation

- `name`: Defines the workflow name displayed in GitHub Actions.
- `workflow_dispatch`: Allows the workflow to be started manually.
- `jobs`: Defines the jobs in the workflow.
- `runs-on`: Selects a runner with the required labels.
- `steps`: Lists the commands executed by the runner.
- `hostname`: Identifies the machine executing the job.
- `uname -a`: Displays operating system and kernel details.
- `df -h`: Displays disk space usage.
- `echo`: Prints a confirmation message in the job logs.

## Step 6: Run the Workflow

1. Commit `.github/workflows/self-hosted-runner.yml` to the repository's default branch.
2. Open the **Actions** tab.
3. Select **EC2 Self-Hosted Runner Lab**.
4. Click **Run workflow**.
5. Open the resulting workflow run and select the `inspect-ec2` job.
6. Review the output of each step.

The workflow completed successfully and produced the following observations:

| Check | Observed result |
|---|---|
| Workflow status | Success |
| Runner hostname | `ip-172-31-1-168` |
| Operating system | Ubuntu Linux on x86-64 |
| Root filesystem | Approximately 24 GB |
| Available root disk space | Approximately 21 GB at the recorded run |
| Confirmation step | `My GitHub Actions job ran on AWS EC2!` |

Resource values can change between executions. The values above reflect one recorded run.

## Step 7: Install the Runner as a systemd Service

After verifying the interactive runner, stop the interactive process with `Ctrl+C` if it is still running.

From the runner installation directory, install and start the service:

```bash
cd ~/actions-runner
sudo ./svc.sh install
sudo ./svc.sh start
sudo ./svc.sh status
```

The service status confirmed:

- The runner service was installed.
- The service was enabled.
- The service state was `active (running)`.

Installing the runner as a service allows Linux to manage the runner process and start it automatically during system boot. The EC2 instance itself must still be running for jobs to execute.

Do not run the interactive runner and service simultaneously for the same runner registration.

## Troubleshooting

### SSH connection times out

- Confirm the EC2 instance is running.
- Verify that the security group allows SSH from your current public IP.
- Check the subnet route table and internet connectivity.
- Confirm that you are using the current public IP address.

### SSH rejects the private key

On WSL, keep the PEM file inside the Linux home directory and restrict its permissions:

```bash
chmod 400 ~/.ssh/self_runner_lab.pem
```

### Runner is offline

- Check that the EC2 instance is running and has network connectivity.
- Check the runner status:

```bash
sudo ./svc.sh status
```

- Review the service logs:

```bash
sudo journalctl -u 'actions.runner.*.service' -n 100 --no-pager
```

If multiple runner services exist, identify the exact service name and inspect that service's logs.

### Workflow is queued but not running

- Confirm that the runner is online in GitHub.
- Verify that the workflow's `runs-on` labels match the runner's labels.
- Confirm that the runner is registered to the correct repository or runner group.
- Check whether the runner is already executing another job.

## Security Best Practices

- Do not publish registration tokens, private keys, access keys, or other credentials.
- Use a dedicated security group and restrict inbound SSH access.
- Avoid running untrusted pull-request workflows on self-hosted machines.
- Be particularly careful with public repositories because external contributors may submit pull requests containing untrusted code.
- Prefer a private practice repository for initial experiments.
- Use least-privilege AWS IAM permissions.
- Keep the operating system and runner software updated.
- Stop or terminate unused EC2 resources to control costs.
- Remember that stopping an instance may not eliminate EBS storage and public IPv4 charges.
